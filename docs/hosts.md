# Host setup and workspace trust

Install the user hooks once. Claude Code, Codex and Antigravity each have **Preview** status. Run `flinch setup --plan` to see the files and commands for installed hosts. After reviewing the plan, apply it with `flinch setup`. Use `--host claude`, `--host codex` or `--host antigravity` to select one host. Start a new local session, then run `flinch doctor` in the checkout to see its status. [Installation](install.md)

| Local host | What setup installs | When a hook can work |
| --- | --- | --- |
| Claude Code in Desktop or the CLI | User hooks in `~/.claude/settings.json` under the default profile | The profile trusts the clone, the Desktop session identifies the clone, or the developer ran `flinch enable` there. |
| Codex in the desktop app or CLI | User hooks in `$CODEX_HOME/hooks.json`, normally `~/.codex/hooks.json` | The user approved the hooks and the base Codex configuration trusts the workspace. A saved profile revocation or a detectable organization policy disables activation. |
| Antigravity App, IDE or CLI | The Flinch directory under `~/.gemini/config/plugins/`, with `plugin.json` and `hooks.json` | The worktree appears in the user's saved trusted workspaces or the user enabled Flinch explicitly in this clone. |

Hook commands target the stable user executable. Flinch checks trust on each event and stays inactive outside Git or when the event cannot identify a worktree. Run `flinch pause` to pause the clone and its linked worktrees, launch a host with `FLINCH=off` to disable that session, or use `flinch setup --remove` to remove the user installation. Repository-defined command and script checks require a separate authorization with `flinch allow-commands` after reviewing their contents. [Workspace trust and limitations](limitations.md)

## Claude Code

In Desktop, open **Code**, choose local execution and select the repository. In the CLI, start Claude Code in the repository. Flinch accepts a positive `projects[<repository root>].hasTrustDialogAccepted` record in `~/.claude.json`. A custom `CLAUDE_CONFIG_DIR` selects the profile's `.claude.json`. On Windows, either separator and any spelling of the drive or directory name's case can match. A positive match authorizes the clone even if another spelling has a false entry. [Workspace trust](https://code.claude.com/docs/en/hooks#workspace-trust) · [Claude's saved project key](https://github.com/anthropics/claude-agent-sdk-python/blob/6fc539e0bffc4ca25648c3d5ee7e04cdcf9f5463/scripts/trust_workspace.py#L12-L55)

Flinch also accepts `CLAUDE_CODE_ENTRYPOINT=claude-desktop` when the event directory and the absolute `CLAUDE_PROJECT_DIR` resolve to the same Git common directory. Claude keeps the project directory at the main checkout in a Desktop-created worktree. Flinch verifies the worktree's Git registration in both directions. Entering an independent checkout changes the event directory and requires authorization for that clone. A missing Desktop marker or an invalid project directory leaves the saved trust and explicit grant as the available signals. To grant access in a reviewed clone, including for headless and SDK sessions, run `flinch enable`. [Hook working directories](https://code.claude.com/docs/en/hooks#reference-scripts-by-path) · [Desktop worktrees](https://code.claude.com/docs/en/worktrees#what-worktrees-share-with-the-main-checkout)

`flinch doctor` and `flinch setup --plan` evaluate the environment in which you run them. A separate terminal can show the clone as inactive even when a Desktop session supplies a matching project directory.

Flinch listens for `UserPromptSubmit` and `Stop`. It sends its first activation notice and a successful reused-check notice through `systemMessage`. When the agent authors a protection, its final response carries the result. Claude documents `systemMessage` as a user-facing warning. The desktop trial below checks its location and visibility for the tested build. [Hook output](https://code.claude.com/docs/en/hooks#json-output)

## Codex

Open a **local Codex** chat on the repository root in the desktop app, or start the CLI there. Review the Flinch handlers for `UserPromptSubmit` and `Stop` in **Review hooks** in the composer or **Settings → Hooks**. The CLI uses `/hooks`. Codex skips a user hook until the developer trusts its definition. In Codex 0.172.0 the approval covers the normalized event and handler declaration. Updating the executable behind the same absolute path, symlink or shim preserves that identity if the handler and its registration stay in place. [Hook review](https://learn.chatgpt.com/docs/hooks#review-and-trust-hooks) · [Versioned user-hook identity](https://github.com/openai/codex/blob/3d86e43b075adeba2193ec5c22ac92f55afd82e6/codex-rs/hooks/src/engine/discovery.rs#L819-L874)

User hooks can fire in an untrusted Codex project. With the default Git project marker, Flinch looks for a decision in the event directory, then the checkout root, then the main checkout of a registered linked worktree. A saved denial for an enclosing `.codex` project layer can veto an inherited grant. Trusting the main checkout covers its subdirectories and registered worktrees unless a more specific decision applies. A custom `project_root_markers` setting requires an exact directory grant. [Workspace trust and configuration layers](limitations.md#codex) · [Codex 0.172.0 workspace lookup](https://github.com/openai/codex/blob/3d86e43b075adeba2193ec5c22ac92f55afd82e6/codex-rs/config/src/loader/mod.rs#L1124-L1149)

Flinch reads organization policy from the copy Codex saves on disk. A bundle containing any configuration or requirements fragment, or an unreadable cache, keeps Flinch inactive. If Codex applies a policy it could not save, Flinch cannot see that policy and follows the user's trust when the cache is absent or still contains an empty bundle. The clone grant applies only to Claude Code and Antigravity. [Codex cache](https://github.com/openai/codex/blob/3d86e43b075adeba2193ec5c22ac92f55afd82e6/codex-rs/cloud-config/src/cache.rs#L28-L52) · [Cache write failures](https://github.com/openai/codex/blob/3d86e43b075adeba2193ec5c22ac92f55afd82e6/codex-rs/cloud-config/src/service.rs#L382-L406)

Codex receives the first activation notice and a successful reused-check notice as `systemMessage`. The protocol describes a warning in the UI or event stream. The 0.172.0 CLI renders a successful hook warning in the transcript. Desktop placement needs an observation on the installed app build. [Output contract](https://learn.chatgpt.com/docs/hooks#common-output-fields) · [CLI history rendering](https://github.com/openai/codex/blob/3d86e43b075adeba2193ec5c22ac92f55afd82e6/codex-rs/tui/src/history_cell/hook_cell.rs#L271-L330)

## Antigravity

Open the project locally in the App, the IDE or the CLI. Setup places a user plugin directly in the directory Antigravity discovers. In the IDE agent side panel, **… → Customizations → Hooks** shows the hooks. Flinch handles `PreInvocation` and `Stop`. One human request can produce multiple invocations. [Plugin structure and installation](https://antigravity.google/docs/build-plugins) · [Hook reference](https://antigravity.google/docs/hooks)

The CLI stores trusted folder paths in `trustedWorkspaces` in `~/.gemini/antigravity-cli/settings.json`. Flinch looks for the checkout, accepting either Windows path separator. The App and IDE can lack that record. In that case, run `flinch enable` once in the reviewed clone. Run `flinch disable` to revoke the explicit grant for Claude Code and Antigravity. If an independent host trust record still exists, remove it in the host or pause Flinch in the clone. [CLI settings](https://antigravity.google/docs/cli/reference)

Antigravity's documented Stop continuation sends feedback to the model and extends the turn. Flinch lets a proved reuse finish without an extra invocation. The initial activity notice is available in `flinch doctor`, and `flinch doctor --all` lists previously active checkouts. The proved reuse is recorded locally. The App and standalone IDE require separate desktop trials. [Stop decisions](https://antigravity.google/docs/hooks#stop)

## Record and verify a desktop session

Use a disposable local clone per app and a second independent clone for controls. Record the app build, execution OS and architecture, and whether Windows uses native execution or WSL. For a sanitized event recording, fully quit the app, set `FLINCH_RECORD=1` in its launch environment, and reopen it there. Check for new JSON files in `<git-common-dir>/flinch/recordings/` after an active turn. Check the file contents before sharing. Remove the setting from the launch environment and restart the app after the trial.

| App | Verify trust before the first active turn | Record the host-specific behavior |
| --- | --- | --- |
| Claude Code Desktop | In a disposable profile with user hooks installed, open clone A in **Code → Local**. Check whether the profile already trusts A. With no saved record or clone grant, submit an ordinary prompt in A, then repeat in a Desktop-created worktree of A. | Compare the parent and child events using the instructions below. Record the location of the first activation notice and the successful reuse notice. Change the event directory to an independent checkout with no grant and confirm the parent session leaves it untouched. |
| Codex desktop | Start a fresh local chat at the disposable repository root. Record the host's folder trust choice, approve the user hooks, and inspect the active user `config.toml` for the saved root entry, preserving its original capitalization. | With default project markers, open chats in a subdirectory and a linked worktree with only the main checkout trusted. Confirm activation in each. Submit the correction and record `UserPromptSubmit`, `Stop`, any continuation, and the notice's location. Set the worktree's own entry to `untrusted` and confirm the next event leaves state untouched. |
| Antigravity App and IDE, separately | Open the disposable clone as the sole workspace. Check the saved CLI trust list and `flinch doctor`. With no host entry or explicit grant, submit an ordinary request and verify no state appears. Use `flinch enable` in that clone, then start another local chat. | Submit the correction and inspect all `PreInvocation` events and the final idle `Stop`. On Windows, record whether the final Stop actually arrived. Check activity with `flinch doctor`. Revoke the explicit grant and repeat the inactive control with the host trust entry also absent. |

To compare Claude Desktop and a child session, record one ordinary prompt in A. Give a separate disposable clone B an explicit grant so the recorder can observe the child even when the marker is absent. From Desktop's shell in A, start `claude -p` in B with a short prompt. Compare one `UserPromptSubmit` recording from each clone. The Claude environment fields record the presence of the entrypoint, project directory, child-session marker and `CLAUDECODE`, whether the entrypoint is exactly `claude-desktop`, whether the project directory belongs to the event's clone and to its checkout, and whether the environment session ID matches the payload. The first two comparisons are the ones the trust gate uses: a child session with `entrypoint_desktop` and `project_dir_same_clone` both true would pass the Desktop check on its own. Keep the environment values private. Repeat with a fresh pair of sessions before drawing conclusions about a child-only signal. Revoke B's grant after the trial.

For acceptance, ask the agent to implement a retry delay in an existing table-driven test fixture, then correct the behavior in ordinary language: “An explicit zero should retry immediately. An omitted delay should keep the default.” Review the diff, the proved case, the passing neighbor and the notice. In a separate trial, exercise a correction requiring an agent-authored check. In the second clone, the project's ordinary test command should reject the repeated bug and pass the omitted-delay neighbor. Record any intervention needed to reach those results. Compare working files, the index and ignored files before and after each trial, and compare the Git common directory in inactive controls. Report which surfaces and scenarios actually ran.

### Orca and T3 Code on Windows

Flinch receives events from the Claude Code or Codex process that the orchestrator launches. Use the same retry-delay fixture, correction and independent control clone described above. Each cell tracks a separate Windows trial. The versions below identify the upstream configuration references. All six cells await a recorded session.

| Orchestrator and launch mode | Claude Code | Codex |
| --- | --- | --- |
| Orca 1.4.277, terminal (PTY) | Not verified | Not verified |
| Orca 1.4.277, Native Chat (structured chat) | Not verified | Not verified |
| T3 Code 0.1.12, worktree thread | Not verified | Not verified |

**Prepare the worktree.** Use a published Flinch release in a Windows lab with a signed-in host. Record its version, the orchestrator build, the host CLI and SDK versions where applicable, and the OS and architecture of the machine running the agent. Distinguish native Windows from WSL. In Orca, confirm how the session launched. A terminal-backed chat or a fallback to a terminal exercises the PTY row. In T3 Code, choose **New worktree**. Set `FLINCH_RECORD=1` in the environment of the process that launches the agent, including the T3 server for a remote session. [Orca chat modes](https://github.com/stablyai/orca/blob/v1.4.277/docs/site/content/docs/agents/native-chat.mdx) · [T3 workspace choices](https://github.com/pingdotgg/t3code/blob/v0.1.12/docs/user/keybindings.md#L33-L39)

From the worker's checkout and effective profile, capture `flinch doctor --json`. Record the checkout directory, whether `CLAUDE_CONFIG_DIR` or `CODEX_HOME` selects a separate profile, and the workspace trust decision. For Codex, review the user hooks in that profile. Orca enables workspace pre-trust by default and lets a repository opt out. T3 supports separate Claude configuration directories and either independent Codex homes or a shadow home that shares configuration. An unrelated terminal can resolve a different profile or executable. [Orca pre-trust](https://github.com/stablyai/orca/blob/v1.4.277/src/shared/agent-launch/permissions/agent-workspace-trust-decision.ts#L1-L23) · [T3 Claude profiles](https://github.com/pingdotgg/t3code/blob/v0.1.12/docs/user/providers-claude.md#L20-L38) · [T3 Codex profiles](https://github.com/pingdotgg/t3code/blob/v0.1.12/docs/user/providers-codex.md#L70-L101)

Run the fixture's ordinary test in the new worktree before the first prompt. For Python, install the fixture dependencies in its virtual environment and put that environment's `pytest` on the agent process's `PATH`. For Vitest or Jest, install dependencies for that worktree's lockfile. Orca can run `scripts.setup` or materialize compatible dependencies through **Worktree Shared Paths**. T3 can run a project action on worktree creation. Wait for setup to finish and record the runner version. [Orca worktree setup](https://github.com/stablyai/orca/blob/v1.4.277/docs/site/content/docs/model/orca-yaml.mdx) · [T3 worktree actions](https://github.com/pingdotgg/t3code/blob/v0.1.12/docs/user/multi-repo-projects.md#L173-L180)
